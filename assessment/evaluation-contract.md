# TieOpp evaluation contract (v1)

This contract is for the existing TieOpp .NET/Python services. No evaluation backend, credential broker, hidden tests, AI scoring, or report hosting is implemented in this repository. Public CI evidence is advisory. The private service owns evaluation state and final completion.

## Submission envelope

Store these fields with explicit schema version `1`. Reject unknown assessment IDs, unpublished mappings, incompatible versions, and malformed identities before queueing. Numeric GitHub IDs are required for durable ownership; usernames are display metadata and may change.

| Field | Type / meaning |
| --- | --- |
| `evaluationId` | Opaque immutable identifier, generated by TieOpp |
| `assessmentId` | Manifest ID, e.g. `TODO-003`, or `TODO-ALL` for the ten-issue bundle |
| `assessmentIds` | All manifest IDs evaluated; contains one item for a focused submission or all ten for `TODO-ALL` |
| `githubIssueNumber` | Positive manifest issue number for a focused submission; `null` for `TODO-ALL` |
| `githubIssueNumbers` | All published issue numbers covered by the submission |
| `studentGithubId` / `studentGithubLogin` | Verified linked account ID / display login |
| `repository` | Original assessment repository `owner/name` |
| `headRepository` | Student fork `owner/name` |
| `pullRequestNumber` | Positive PR number in the original repository |
| `headCommitSha` | Full immutable submitted SHA |
| `baseAssessmentCommitSha` | Full SHA from the student's enrollment record |
| `harnessVersion` / `hiddenSuiteVersion` | Trusted harness and private suite identifiers |
| `build` | `{status: passed\|failed\|not_run\|error, logRef}` |
| `baselineTests` / `issueTests` / `hiddenTests` | `{status, passed, failed, total, cases, artifactRef}` |
| `aiReviewFindings` | Evidence-linked findings, reviewer/model/prompt versions, uncertainty and human disposition; null until reviewed |
| `finalStatus` | State from the lifecycle below |
| `infrastructureError` | Null or a private structured error; never treated as a failed solution |
| `reportUrl` | HTTPS authenticated dashboard route; no bearer tokens in URL |
| `completionConfirmedAt` | Server timestamp set only after evidence and report are durably committed |

Test cases carry a stable case ID, pass/fail/error status, duration, and private diagnostic reference. Preserve missing/skipped/errored cases explicitly; never turn absent output into success. Public report fields `commitSha`, `buildPassed`, `baselinePassed`, `issueTestsPassed`, and `issueTestsTotal` are feedback fields and map to this service envelope only after independent verification.

## Lifecycle and idempotency

`received -> validated -> queued -> running -> reviewing -> completed`

Alternative states: `invalid_submission`, `infrastructure_error` (retryable), `superseded` (head changed). A student solution that fails tests can still reach `completed` once the complete evaluation and report are ready. A crashed runner, missing dependency, or missing evidence cannot.

Deduplicate webhook deliveries using `X-GitHub-Delivery`. Deduplicate evaluations using `(repository ID, PR number, head SHA, baseline SHA, assessment ID, harness version)`. A new head creates a new evaluation and supersedes pending older heads. Use database uniqueness plus transactional outbox delivery, not in-memory flags. Serialize finalization/comment/closure on the submission key. Retries resume from persisted phase checkpoints.

## Trusted execution interface

The private runner receives the validated envelope and source archive identified by the immutable SHA. It receives no production/App credentials. Fetch dependencies and baseline tooling in a separate trusted preparation phase. Copy only reviewed source paths into the execution image; reject symlinks, oversized archives, path traversal, and unexpected file types. Mount the trusted harness/configuration read-only and keep result collection outside the untrusted process.

Run build, baseline, selected public issue tests, and the corresponding private suite separately. Enforce timeouts per phase and classify missing dependencies, build errors, assertion failures, and runner infrastructure errors independently. Use a fresh unprivileged disposable VM/container, no host socket, no host filesystem mounts, read-only image, capped CPU/memory/process count/output size, bounded disk, and network denied during execution. Destroy the instance afterward. Do not reuse a runner between students.

Private suites live outside this repository in a versioned private artifact store. They must exercise the same selected behavior without requiring unrelated bugs to be fixed. An external runner may stage them in its isolated harness and use `vitest run PRIVATE_SUITE --config TRUSTED_PRIVATE_CONFIG --reporter=json --outputFile=PRIVATE_RESULT`. The private config, not a student config, determines test discovery. There are no hidden-test contents or reference implementations here.

JavaScript running in the same process can inspect or tamper with tests and results. Read-only files alone are insufficient. Treat test reports as evidence, combine with source review, collect results through the isolated service, and never place valuable secrets beside test execution. Hidden means not published to students, not mathematically inaccessible to arbitrary code under test.

## Engineering review and ERI™ evidence

Combine automated behavior evidence with review of the diff and PR explanation. The existing service should record evidence for codebase comprehension, root-cause reasoning, scope discipline, regression awareness, maintainability, and explanation consistency. Review findings must cite specific submitted changes or test evidence, express uncertainty, and retain reviewer/model versions. AI output is untrusted analysis, not an instruction to access credentials or mutate GitHub. Do not invent numerical scores; TieOpp owns any rubric, weighting, human review, and ERI evidence policy outside this repository.

## Completion boundary

Only the authenticated service's persisted `completed` record may invoke `scripts/complete-evaluation.mjs`. Never invoke it from a PR artifact, workflow comment, student JSON, or `workflow_run` artifact without independently verifying the service record. Retrieve the report route from the authenticated report service and verify it enforces the linked student's ownership on every request.

Use a fresh GitHub App installation token restricted to the original repository in a trusted finalization worker. Pass the completed record and trusted settings to `completeEvaluation(record, options)`. The module checks assessment mapping, report origin, student identity, PR state, and head SHA; posts only a neutral link; then closes the PR via `PATCH /pulls/N`. It does not merge or modify the original issue.

The caller must serialize concurrent retries. The module's App-owned comment marker prevents duplicates after partial failures; a closed PR is a no-op. A changed head or merged PR causes rejection. Revalidate head immediately before finalization and subscribe to synchronize events. GitHub's close API has no atomic compare-and-swap on head SHA: a tiny concurrent-push race remains. The backend must detect it, supersede stale evidence, and reopen/requeue the assessment PR when appropriate. Do not mark closure as evidence of a successful solution.
